    Architecture¶

    How Saveroom is put together: the services that run, how the code is organised, and how a change travels from one browser to every other open tab. Read this first if you are going to operate, debug or change Saveroom.

    At a glance¶

    Saveroom is two applications plus background workers:

    • Backend: a Django application, served as ASGI by gunicorn with uvicorn workers. It owns all state and exposes it through the REST API (/api/) and a WebSocket endpoint (/ws/). It has no user interface of its own.
    • Web frontend: a Nuxt (Vue) application. Its Node server renders the first page (SSR); the browser then talks to the backend directly.
    • Celery workers: the default worker runs realtime broadcasts and automations. The export worker runs jobs (imports, exports, duplication, snapshots, backups), webhooks, search indexing, notification emails and cleanup. Beat schedules periodic tasks.
    • PostgreSQL stores everything, including the tables users create.
    • Redis is the Celery broker, the beat schedule store, the Channels (WebSocket) layer and the cache.
    • Media storage holds uploaded files. It is a local directory by default, or S3, GCS or Azure Blob storage.

    Two worker queues

    Most background work is bound to the export Celery queue: run_async_job (every job), webhooks, search indexing, notification emails, backups, scheduled exports and cleanup tasks (queue="export" in the tasks.py modules and CELERY_TASK_ROUTES in backend/src/baserow/config/settings/base.py). Every deployment therefore runs a celery-exportworker next to the default celery-worker: exportworker in the all-in-one image, celery-export-worker in docker-compose.yaml and the celery-export Deployment in the Helm chart. With BASEROW_RUN_MINIMAL and BASEROW_AMOUNT_OF_WORKERS=1 the default worker takes both queues and the export worker idles.

    Backend¶

    Django apps¶

    backend/src/baserow/ is split into a small core and optional apps under contrib/. Every app plugs its types into shared registries, so the core never imports a contrib app directly.

    flowchart TB
    config[config<br/>settings, urls, asgi, celery]
    api[api<br/>DRF views for core]
    ws[ws<br/>Channels consumer, page types, broadcasts]
    core[core<br/>users, workspaces, applications, jobs,<br/>trash, actions, registries, permissions,<br/>backups, snapshots, notifications, sso]

    subgraph contrib[contrib: application types]
        database[database<br/>tables, fields, rows, views,<br/>formula, webhooks, export, search]
        builder[builder<br/>pages, elements, data sources,<br/>workflow actions, domains]
        automation[automation<br/>workflows, nodes, triggers]
        dashboard[dashboard<br/>widgets, data sources]
        integrations[integrations<br/>local_baserow, core: HTTP/SMTP, slack]
    end

    config --> api & ws & core
    api --> core
    ws --> core
    database & builder & automation & dashboard & integrations -->|register types in| core
    builder & automation & dashboard -->|use services from| integrations
    integrations -->|local_baserow reads| database
    Package Responsibility
    config/ Settings (settings/base.py), URL root, asgi.py (HTTP plus WebSocket router), celery.py, read-replica DB router
    core/ Users, workspaces, the application abstraction, jobs, trash, undo/redo actions, registries, permission managers, backups, snapshots, notifications, OIDC SSO, data destinations
    api/ REST endpoints for core concepts, mounted under /api/
    ws/ CoreConsumer at /ws/core/, page types (who subscribes to what), broadcast tasks, presence

    contrib/integrations/ Service and integration types that builder, automation and dashboard nodes call

    Third-party plugins load as extra Django apps through BASEROW_BACKEND_PLUGIN_NAMES (see Plugins).

    Layers inside a feature¶

    Each feature follows the same stack. API views stay thin, and the rest can be called from views, Celery tasks, management commands or tests alike.

    flowchart TB
    view["API view + serializer<br/>(api/…/views.py)"]
    action["Action type<br/>(actions.py): do / undo / redo"]
    service["Service<br/>(builder, automation, integrations)"]
    handler["Handler<br/>(handler.py): business logic + DB writes"]
    perms["Permission check<br/>CoreHandler().check_permissions"]
    model[("Models<br/>Django ORM")]
    signal["Django signal<br/>(signals.py)"]
    wsrecv["ws receivers<br/>broadcast on commit"]

    view --> action
    view --> service
    action --> handler
    service --> handler
    handler --> perms
    handler --> model
    handler --> signal
    signal --> wsrecv
    • Handlers (*Handler) hold the business logic. Example: RowHandler.update_rows in contrib/database/rows/handler.py.
    • Action types wrap handler calls that users can undo. See the undo/redo guide.
    • Services add permission checks and dispatch for the builder, automation and integration domains.
    • Registries hold pluggable Instance types: field types, view types, application types, element types, permission managers and so on. See the permissions guide and database plugin.
    • Signals fan out side effects such as realtime broadcasts, webhooks, notifications and search indexing without coupling them to the handler.

    erDiagram
    USER }o--o{ WORKSPACE : "member of"
    WORKSPACE ||--o{ APPLICATION : contains
    APPLICATION ||--o| DATABASE : "is a"
    APPLICATION ||--o| BUILDER : "is a"

    APPLICATION ||--o| DASHBOARD : "is a"

    TABLE ||--o{ FIELD : "has columns"
    TABLE ||--o{ VIEW : "has views"
    TABLE ||--|| USER_TABLE : "rows stored in database_table_N"

    Each user-created table is a real PostgreSQL table named database_table_<id>, with one column per field (field_<id>). The backend builds a Django model for it on the fly with Table.get_model(). See Table persistence.

    Async work¶

    flowchart LR
    req[API request / handler] -->|"JobHandler.create_and_start_job"| redis[(Redis broker)]
    beat[celery beat] -->|periodic tasks| redis
    redis -->|"queue: celery<br/>automation_workflow"| worker[default worker<br/>realtime broadcasts,<br/>automation workflows]
    redis -->|"queue: export"| export[export worker<br/>jobs, webhooks, search index,<br/>emails, backups, cleanup]
    worker & export -->|state + progress| pg[(Job rows in PostgreSQL)]
    pg -->|"GET /api/jobs/{id}/"| client[web-frontend]

    Long operations run as jobs: a database row tracks state and progress, and a Celery task does the work. See the jobs pattern.

    web-frontend/modules/ mirrors the backend apps. Each module is a Nuxt module that registers routes, Vuex stores and *Type classes into the client-side registry.

    Request flow: editing a cell¶

    This flow shows most of the architecture in one pass: REST, an undoable action, the handler, a signal, Celery and the Channels layer.

    sequenceDiagram
    autonumber
    participant A as Browser A
    participant P as Proxy
    participant B as Backend (ASGI)
    participant DB as PostgreSQL
    participant Q as Redis
    participant W as Celery worker
    participant C as Browser B

    A->>P: PATCH /api/database/rows/table/{id}/{row_id}/
    P->>B: forward
    B->>B: RowView.patch → UpdateRowsActionType.do
    B->>DB: RowHandler.update_rows → UPDATE database_table_{id}
    B->>B: rows_updated signal → broadcast on commit
    B-->>A: 200 updated row
    B->>Q: broadcast_to_channel_group.delay(...)
    Q->>W: task
    W->>Q: channel_layer.group_send("table-{id}")
    Q->>B: deliver to CoreConsumer sockets
    B-->>C: rows_updated event over /ws/core/
    C->>C: database/realtime.js updates Vuex store

    The sender's web_socket_id is excluded from the broadcast, so browser A doesn't apply its own change twice. For more, see WebSockets and Realtime presence.
